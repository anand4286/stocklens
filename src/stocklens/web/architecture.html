How StockLens is built

One stateless FastAPI service. Inside it, five engines of pure functions — scoring, quant, research, forecasting and evidence — feed a single report that the page, the AI agent and the evaluation harness all read. Around it, a closed loop that commits forecasts, grades them, and decides whether the model has earned its weights.

The idea in one picture: a model that keeps score

Most analytics stacks end at "show the number". StockLens's architecture is organised around what happens after: every claim is committed, checked against what happened, and fed back.

System architecture

The engines

Every engine is pure Python over plain dataclasses and lists: no I/O, no framework, no NumPy (ADR 0005). That is what lets one report serve three consumers, and lets every estimator be tested against a seeded null.

Lifecycle of one stock page (~250 ms)

  1. Ticker validated against ^[A-Z]{1,5}([.-][A-Z]{1,2})?$ before it can reach any upstream URL.
  2. Three years of bars for the stock, the benchmark and its sector fund, plus news and filings — each through a TTL cache.
  3. Regime first: corrected Hurst and variance ratio must agree, and the result tilts the family weights.
  4. Eight families score or abstain; the blend shows every contribution.
  5. Risk, GARCH, probabilistic Sharpe, volume profile and analogs; factor attribution and a 2,000-path filtered historical simulation; forensic scores and the DCF grid.
  6. The forecast is built from the same bars and committed to the ledger — once per session — and any due forecasts for the symbol are resolved.
  7. One JSON report goes to the page; the agent later reads the same object through its tools.

The evidence lab re-scores ~500 past sessions (~0.5 s), so it is a separate, cached endpoint loaded when its tab opens.

How the estimators are tested

Each one is tested twice: on a seeded null, where it must find nothing, and on a planted signal, where it must find it. 248 tests, about 20 seconds, no network.

  • Analog search: 5% false positives on random walks (was 9% with the naive standard error — fixed).
  • Regime detector: 100 of 100 random walks called "random".
  • Evidence lab: 0 false "works" across 20 demo symbols and 40 random walks after adding a circular-shift test; the plain permutation test alone gave 7–9%.
  • Track record: a 5-symbol random basket earned "skill" on the plain interval; the block t-test now refuses it.
  • Point-in-time: mutating future bars must leave every past forecast and score unchanged.

Agent loop

Ten read-only tools bound server-side to one symbol, plus submit_report. No tool takes a ticker, URL or query. The loop has a step ceiling, handles every stop reason, re-validates the submission with Pydantic and checks each cited figure against what the tools actually returned. Runs are cached, budgeted per day, rate-limited, and written to an audit table.

Security and deployment

Strict CSP with no inline script, HSTS, constant-time key comparison, secrets as SecretStr. Non-root read-only container; egress restricted to the model API, market data and SEC. Templates for Compose with Caddy, systemd + nginx + ufw, Kubernetes with NetworkPolicy, Cloud Run, AWS App Runner/ECS and Azure Container Apps.
